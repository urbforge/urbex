# ADR-0028: PostgreSQL databases for projects

## Status

Proposed. Part of [urbforge/redemptor#17](https://github.com/urbforge/redemptor/issues/17)
(tracked by [urbforge/urbex#6](https://github.com/urbforge/urbex/issues/6));
implemented by [urbforge/urbex-cli#9](https://github.com/urbforge/urbex-cli/issues/9).
Follows the service conventions of [ADR-0027](0027-service-conventions.md).

## Context

A project's services have nowhere to keep structured data. A Postgres
run inside a service's container is lost when its LXC is re-created, its
credentials are managed by hand, and nothing about it follows the
platform's conventions (Komodo, internal DNS, Grafana, exposure, kind).
The product's target stack names Postgres for persistence.

The design touches the topology ([ADR-0009](0009-one-lxc-per-service-per-env.md)),
secrets ([ADR-0011](0011-secrets-sops-age.md)), internal DNS
([ADR-0026](0026-technitium-internal-dns-records.md), [ADR-0027](0027-service-conventions.md))
and what `urbex destroy` deletes.

## Decision

### Where Postgres runs: its own LXC per project environment

Each database a project declares runs in **its own LXC per environment**,
`<project>-<database>-<env>`, like a service (ADR-0009): one Postgres
server, one database in it. Staging and production never share data,
resources are sized per database, upgrades and destroy concern one
project environment at a time.

Rejected: one platform Postgres with a database per project environment -
fewer LXCs, but a noisy project slows every other, one upgrade moves every
project at once, and destroying an environment means dropping a database
inside a shared server instead of removing an LXC.

### Manifest

A top-level `databases` list declares them; a service lists the
databases it uses:

```yaml
databases:
  - name: main            # the database's name, unique in the project
    engine: postgres      # the only engine for now
    version: "17"         # PostgreSQL's major version
    resources:            # the LXC's, as a service's (disk default 10Gi)
      disk: 20Gi

services:
  - name: api
    runtime: go
    port: 8080
    databases: [main]
```

`schemas/urbex.schema.json` gets `databases` (name, engine, version,
resources) and `services[].databases`; a service may only name a declared
database, and a database's name may not be a service's.

### Connection

- **Internal name**: `<database>.<project>.<zone>` in production,
  `<database>.staging.<project>.<zone>` in staging (ADR-0027), an A record
  in Technitium set by `apply` and removed by `destroy`. Services reach it
  only by that name.
- **What a service gets**, in its environment, for each database it uses:
  `DATABASE_URL`
  (`postgres://<user>:<password>@<name>:5432/<database>`) and the
  `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` variables most
  drivers read. A service using more than one database gets them prefixed
  with the database's name in capitals: `MAIN_DATABASE_URL`, `MAIN_PGHOST`...
- **Credentials**: generated by the first `apply` of the environment - a
  user named after the project and a random password - and kept
  SOPS-encrypted in the GitOps repo: the database's own folder
  (`environments/<env>/<project>/<database>/secrets.sops.env`, the
  Postgres container's `POSTGRES_PASSWORD`) and the secrets of each
  service using it (`DATABASE_URL`, `PGPASSWORD`). Re-applying reuses
  them. Rotation is out of scope for now: changing the password by hand
  means updating both places.

### Komodo, monitoring, observability

The database is a project component like a service (ADR-0027, kind
`app`):

- its LXC is a Komodo Server (Periphery), tagged `app`, the project and
  the environment;
- the official `postgres:<version>` image runs as the Komodo Stack
  `<project>-<database>-<env>`, from its folder in the GitOps repo
  (`compose.yaml`, `config.env`, `secrets.sops.env`), deployed by
  `apply`; its container carries `urbex.kind: app` and
  `urbex.service: <database>`;
- the LXC's telemetry agent (ADR-0027) ships its logs and resources, as
  for every LXC;
- Postgres' own metrics (`postgres_exporter`) come later, with the
  services' own metrics (`observability.metrics`).

In the service catalog it is an app entry with one endpoint, port 5432,
**internal**.

### Lifecycle

- **First `apply`**: creates the LXC, the credentials, the Stack, the DNS
  record, and the services' variables; the services are deployed after
  the database is healthy.
- **Re-applies, redeploys, releases** keep the data: the LXC is changed
  in place by Terraform, never re-created, and the data is a Docker volume
  on its disk.
- **Upgrades**: minor versions follow the image of the declared major
  version, on redeploy. A major upgrade (`version: "17"` to `"18"`) needs
  a dump and restore that Urbex doesn't automate yet: `apply` refuses to
  change the major version of an existing database, and says so.
- **`urbex destroy <env>`** deletes the database's LXC, and so its data.
  Because that can't be undone, `destroy` of an environment that has a
  database refuses to run without `--delete-databases`, naming them -
  in staging as in production.

### Where the data lives

On the LXC's root disk, in the Postgres container's volume. A separate
Proxmox mount point would let the data outlive the LXC, but nothing
re-creates a database's LXC except `destroy`, which is meant to delete
it; one disk keeps Terraform and backups simple. Its size is the
database's `resources.disk` (default `10Gi`), grown in place by
re-applying with a bigger value.

### Access and exposure

The platform's network only - never on Cloudflare, never public. Other
services reach it by internal name; a developer reaches it from the LAN
at the same name (with the router forwarding the zone to Technitium, as
ADR-0027 says) or at the LXC's address, with the credentials from the
GitOps repo (`urbex secret`). A tunnelled or Access-protected admin UI is
out of scope.

### Backups

Out of scope for this decision; tracked separately. Meanwhile, the
database's LXC is backed up like any LXC by Proxmox's backups (vzdump),
and `pg_dump` over the LAN works.

## Rationale

- One LXC per database per environment applies ADR-0009 to data too:
  isolation, sizing and destroy have one meaning everywhere.
- A database is just another project component following ADR-0027:
  nothing special in Komodo, DNS, Grafana or exposure.
- `DATABASE_URL` and `PG*` are what frameworks and drivers read without
  configuration.
- Refusing a silent data loss on `destroy`, and an unautomated major
  upgrade on `apply`, costs a flag or a message; losing data costs more.

## Consequences

- `urbex-cli#9` implements it: manifest and schema, Terraform (the
  database's LXC), Ansible (Docker, Periphery, the agent), the Stack and
  its folder, credentials, DNS, the services' variables, `destroy`'s
  flag, `status`, the e2e and docs.
- Each database costs an LXC per environment.
- No backups, no automated major upgrades, no rotation, no
  connection pooling or replicas yet.
