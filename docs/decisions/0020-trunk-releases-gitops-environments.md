# ADR-0020: Trunk-based projects, tagged releases, environments in the GitOps repo

## Status

Accepted. Supersedes [ADR-0019](0019-branch-environments-komodo-rollouts.md)
(one branch per environment) and replaces the promotion flow of
[ADR-0010](0010-promotion-flow.md) for good. Builds the missing half of
[ADR-0004](0004-gitops-gitea-komodo.md): Komodo reconciling from the
GitOps repo.

## Context

ADR-0019 tied each environment to a branch of the project's repo:
merging into `staging` or `main` rebuilt and redeployed it. That put
environment state in the project repo's branch structure, rebuilt
production instead of promoting an artifact, and left configuration in
two places (the manifest and Komodo). The requirement is now:

- project repos are developed **trunk-based**;
- **releases are Git tags**;
- a **separate GitOps repo** has **one folder per environment**, holding
  that environment's configuration, its secrets (SOPS), and the
  **versions to deploy**;
- Komodo **builds from the project repos** and **deploys from the GitOps
  repo**.

## Decision

### Project repos: trunk and tags

- A project's repo lives on Gitea (`<org>/<project>`) and has one
  long-lived branch, `main`. There are no environment branches.
- A release is a tag `vX.Y.Z` on `main`. Only this form is a release:
  Komodo versions are strictly `major.minor.patch`.

### Builds: one image per release, from the project repo

- Each service has one Komodo **Build**, `<project>-<service>` -
  independent of any environment.
- A Gitea webhook on the project repo calls a Komodo **Action**,
  `urbex-release`, on every push. For a release tag, the Action points
  every Build of that repo at the tagged commit, sets its version to
  `X.Y.Z`, and runs it. Anything else is ignored.
- The image is pushed once, as
  `<registry>/<org>/<project>-<service>:X.Y.Z` (plus a `<commit>` tag),
  and that same image is what every environment runs.

### Environments: folders in the GitOps repo

The GitOps repo (`<org>/gitops`, the one `urbex bootstrap` creates) gets
an `environments/` tree, one folder per environment:

```
environments/
  staging/
    <project>/
      <service>/
        compose.yaml        # how the service runs; generated from urbex.yaml
        version.env         # VERSION=1.4.2 - the release to deploy
        config.env          # non-secret configuration
        secrets.sops.env    # secrets, encrypted with SOPS + age
  prod/
    ...
```

- `version.env` is the **only** thing that decides what an environment
  runs. Deploying, promoting, and rolling back are all a commit that
  changes it.
- `config.env` is the environment's configuration and lives here, not in
  the project repo. `urbex.yaml`'s `env.<environment>` block only seeds
  it the first time; afterwards the GitOps repo is authoritative.
- `secrets.sops.env` is a dotenv file encrypted with SOPS for the
  platform's age key ([ADR-0011](0011-secrets-sops-age.md)), whose public
  half is in `.sops.yaml` at the root of the GitOps repo. The file always
  exists: without secrets it holds only a comment.
- `compose.yaml` is generated by `urbex apply` from `urbex.yaml` (image,
  port, healthcheck) and is owned by Urbex.

### Deploys: Komodo, from the GitOps repo

- Each service in each environment has a Komodo **Stack**,
  `<project>-<service>-<env>`, on that service's LXC, whose source is the
  service's folder in the GitOps repo.
- One Gitea webhook on the GitOps repo calls a Komodo **Procedure**,
  `urbex-gitops`, which redeploys every Stack whose files changed
  (`version.env`, `config.env`, `secrets.sops.env`, or the compose
  file). The Procedure also runs every 15 minutes on its own, so the
  environments converge on the repo even if a webhook is missed.
- A Stack's definition never depends on its folder's contents: it is
  declared once by `urbex apply`, and everything after is a commit.
- Secrets are decrypted on the LXC at deploy time: every Stack runs
  `docker compose up` through a small wrapper installed next to the
  Periphery agent, which, if the secrets file is encrypted, has `sops`
  decrypt it with the platform's age key into a temporary file that
  exists only while compose runs. Plaintext secrets are never written to
  the GitOps repo, nor left on disk.

### CLI roles

- `urbex apply <env>`: infrastructure, Periphery, the project's Builds
  and release webhook, the environment's folder and Stacks. If the
  environment has a version set (a re-apply), it tells Komodo to deploy.
- `urbex release`: tags the next release on `main` and waits for its
  images.
- `urbex deploy <env> [--version X.Y.Z]`: sets `version.env` (default:
  the latest release), commits and pushes the GitOps repo, waits for the
  environment to run it.
- `urbex promote`: sets prod's versions to staging's.
- `urbex secret set|unset|list <env> <service> [KEY]`: manages secrets
  (needs the `sops` binary).
- `urbex status <env>`: desired version (GitOps repo) against the
  running image (Komodo).

Each of `deploy`, `promote`, and `secret set` is only a convenience for
"edit the environment's folder, commit, push": doing that by hand, or
through a pull request on the GitOps repo, has the same effect.

## Rationale

- **Build once, deploy everywhere** comes back: production runs the
  exact image staging ran.
- One place answers "what runs where": the GitOps repo. Its history is
  the deployment log, and rollback is `git revert`.
- Configuration and secrets are per environment, which is where they
  belong, and reviewable where they are changed.
- The project repo is only about the project: no environment branches to
  keep in sync, no merge commits that mean "deploy".

## Consequences

- Nothing is deployed by a push to `main` alone. Staging runs a version
  only when it is released and its `version.env` says so; continuous
  deployment of `main` to staging, if wanted, is a later addition (an
  automatic bump of staging's `version.env`).
- A project's first deploy needs a release: `urbex apply` creates an
  environment that is empty until a version is set.
- The manifest's `env` block stops being authoritative after the first
  apply; changing it later has no effect on an existing environment.
- Every project LXC's Periphery needs `sops` and the age private key.
  The key, until now a required-but-unused credential, becomes
  load-bearing: losing it means re-encrypting every secret.
- Urbex's own pushes to the GitOps repo (Terraform state, inventories)
  trigger the webhook too; Stacks whose folder didn't change are left
  alone.
- Komodo caches a repo for a few seconds after looking at it, so a push
  that lands right after another one (or right after a Stack was
  touched) can be missed by its webhook. The `urbex` commands that push
  ask Komodo to reconcile themselves - `deploy` and `promote` when the
  environment doesn't move, `secret` always; for pushes made by hand, the
  scheduled run catches up within 15 minutes.
- Komodo refuses to deploy a Stack with a tracked file missing, hence
  the always-present secrets file.
- The release Action needs npm access from the Komodo LXC the first time
  it runs (Komodo's scripting runtime fetches its client library).
- Pull requests on the GitOps repo can gate production: branch
  protection on `environments/prod/` is a Gitea setting, not something
  Urbex enforces.
